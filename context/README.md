# Development Context

このディレクトリは、プロジェクトの**実装に必要な背景知識と判断の経緯**を、人間とコーディングエージェントが共有するための Knowledge Base です。

`docs/` は**現在のアプリケーション**の仕様・使い方・API などを説明する場所、`context/` は**なぜその設計や実装に至ったか**を理解するための場所です。エージェントの作業規約はルートの `AGENTS.md` に記述します。

## Organization

必要になったディレクトリだけ作成してください。以下は推奨する分類です。

| Path | Contents |
| --- | --- |
| `references/` | 論文、技術資料、外部仕様、参考 URL とその読書メモ |
| `discussions/` | AI や共同開発者との議論から得られた結論、仮説、未解決事項 |
| `plans/` | 実装計画、マイルストーン、調査・検証の方針 |
| `decisions/` | 採用した設計判断、その根拠、代替案（ADR など） |
| `glossary.md` | プロジェクト固有の用語・記号・概念の定義 |

この分類に収まらない資料は、用途が明確なら別のサブディレクトリを追加して構いません。

## Knowledge Index

プロジェクト固有の資料を追加したら、**ここに短い説明と相対リンク**を追記してください。エージェントが必要な資料を選んで読むための入口として使います。資料の全文をこの README に転記する必要はありません。

## Conventions

- **出典を残す**：参照した論文・資料には、可能な限り著者、タイトル、DOI / arXiv / URL などを記録します。外部資料の全文をコピーする代わりに、リンクと必要な要約を優先します。
- **確度と状態を区別する**：検証済みの事実、仮説、提案、採用済みの決定を混同しないでください。計画・議論・決定の文書には、必要に応じて `Draft`、`Active`、`Completed`、`Superseded` などの状態と更新日を付けます。
- **議論は結論から読む**：長い AI 対話は、問題設定、前提、結論、根拠、未解決事項を要約してから保存します。全文が必要なら要約から参照できるようにします。
- **古い情報を残しつつ明示する**：方針が変わった場合は、古い資料を無条件に削除するのではなく、更新・失効状態や後継文書へのリンクを明記します。
- **実装との整合性を確認する**：`context/` の計画や議論は現在の実装を保証しません。作業時にはコード、テスト、`docs/` と照合し、矛盾があれば明示してください。
- **使い捨ての生成物を置かない**：一時スクリプト、実行ログ、中間出力は `.scratch/<task-slug>/` に置き、再利用・再現する価値のあるものだけを適切な場所へ移します。

## When to Update

新しい参考資料を採用したとき、重要な設計判断を行ったとき、実装計画が変わったとき、あるいは用語の定義が確定・変更されたときに、関連する文書とこの Index を更新してください。

**原則：`docs/` は *what the application does*、`context/` は *why and how we decided to build it*。**
